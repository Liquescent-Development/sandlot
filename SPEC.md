# Sandlot Technical Specification

**Status:** Draft implementation specification
**Project:** Sandlot
**Purpose:** A Pi extension that automatically runs agent-controlled operations inside Anthropic's Sandbox Runtime.

## 1. Summary

Sandlot is a Pi package that creates a fresh Sandbox Runtime policy for every Pi session and routes all model-controlled filesystem, process, and network operations through it.

Pi itself remains a trusted host-side control plane. Model API requests, Pi configuration, session persistence, the TUI, and trusted extension initialization run outside the sandbox. The model-controlled data plane—shell commands, file access, file mutation, search, directory listing, and user `!` commands—runs inside Sandbox Runtime.

This is the strongest security boundary that can be provided automatically by a Pi extension. An extension cannot retroactively sandbox the Pi process that loaded it.

## 2. Goals

Sandlot must:

1. Activate automatically for every Pi session after installation.
2. Initialize one Sandbox Runtime policy per Pi session.
3. Sandbox every built-in coding tool that can access the host:
   - `bash`
   - `read`
   - `write`
   - `edit`
   - `ls`
   - `find`
   - `grep`
4. Sandbox user-entered `!` and `!!` commands.
5. Preserve Pi's normal tool schemas, output formats, truncation, diffs, and rendering.
6. Fail closed. A sandbox failure must never cause local, unsandboxed execution.
7. Protect common credentials, Pi configuration, project-local Pi extensions, and paths outside the workspace by default.
8. Permit user-controlled policies while preventing a project from widening its own permissions.
9. Surface initialization failures and sandbox violations clearly.
10. Work in interactive, print, JSON, and RPC modes without requiring a TUI.

## 3. Non-goals

The first version will not:

- Sandbox Pi's model-provider HTTP requests.
- Treat arbitrary third-party Pi extensions as untrusted code. Pi extensions execute with full host permissions before and outside tool execution.
- Guarantee that code written into the project will be safe when a human later executes it outside Sandlot.
- Transparently sandbox the entire Pi process. That requires a separate launcher and cannot be guaranteed by an extension alone.
- Silently support custom tools that bypass Sandlot. Custom tools must be explicitly trusted or blocked.

## 4. Threat model

### 4.1 Untrusted inputs

Sandlot treats the following as untrusted:

- Commands generated by the model.
- Paths and content supplied to coding tools by the model.
- Network destinations reached by model-generated commands.
- Commands entered through Pi's `!` and `!!` facilities.
- Repository content that may attempt to influence the model into accessing secrets or establishing persistence.

### 4.2 Trusted components

Sandlot assumes the following are trusted:

- The Pi executable and its core packages.
- Sandlot's installed package files.
- User-level Sandlot configuration.
- Other Pi extensions the user has chosen to install.
- Sandbox Runtime and its native platform dependencies.

### 4.3 Security boundary

The security boundary is the Sandbox Runtime child process and its descendants. The host-side extension owns the Sandbox Runtime manager and filtered network proxies. It communicates with sandboxed child processes through controlled standard input/output pipes.

On macOS, shutdown and cancellation kill the wrapper process group and perform best-effort detached-descendant supervision. They cannot guarantee termination of a hostile process that deliberately creates a new session and reparents between observations. A race-free guarantee requires support from Sandbox Runtime or the platform.

The extension must never perform a model-requested filesystem or process operation directly on the host.

## 5. Architecture

### 5.1 Host control plane

The host-side Pi extension is responsible for:

- Loading and validating configuration.
- Composing user and project policies.
- Owning `SandboxManager` lifecycle.
- Registering and overriding Pi tools.
- Starting sandboxed child processes.
- Streaming tool output back to Pi.
- Enforcing cancellation and timeouts.
- Guarding against unsafe tool replacement.
- Reporting status and violations.

### 5.2 Sandboxed data plane

Sandboxed child processes are responsible for:

- Shell execution.
- Reading and inspecting files.
- Writing and creating files or directories.
- Directory listing and metadata queries.
- File search and content search.

Sandbox Runtime enforces policy on the entire child process tree using:

- macOS: `sandbox-exec`/Seatbelt.
- Linux: Bubblewrap, network namespaces, and optional seccomp support.

### 5.3 Invocation model

The initial implementation should use one sandboxed child invocation per tool operation. This provides:

- Strong isolation between calls.
- Accurate per-tool violation attribution using the Pi tool-call ID.
- Straightforward cancellation and timeout behavior.
- No long-lived in-sandbox control process that a child command could attack.

A persistent session worker may be evaluated later if benchmarks show unacceptable overhead. It must not be introduced until equivalent isolation, cancellation, and violation attribution are demonstrated.

### 5.4 Package layout

A suggested layout is:

```text
package.json
README.md
SPEC.md
src/
  index.ts
  config.ts
  policy.ts
  runtime.ts
  runner.ts
  guard.ts
  tools/
    index.ts
    bash.ts
    files.ts
    search.ts
  helpers/
    file-worker.ts
    search-worker.ts
test/
  unit/
  integration/
```

`package.json` should declare the extension entry point under `pi.extensions` so Pi can install and load Sandlot as a normal package.

Pi 0.84.2 is an exact host compatibility prerequisite and development dependency, not an install-time dependency or peer. Pi's extension loader supplies its public APIs; declaring a runtime peer makes Pi's Git install path resolve or install a second Pi tree. Compatibility updates therefore require an explicit reviewed Pi version change and the installed-package smoke matrix.

Sandbox Runtime is a beta research preview. The initial implementation should pin an exact tested version rather than accepting automatic minor updates. At the time this specification was prepared, the current npm release was `@anthropic-ai/sandbox-runtime@0.0.73`.

## 6. Pi lifecycle

### 6.1 Extension factory

The extension factory should only register flags, commands, tools, and event handlers. It must not start proxies, child processes, watchers, or other session-scoped resources.

### 6.2 Session start

On `session_start`, Sandlot must:

1. Enter a non-ready, fail-closed state.
2. Load the trusted user policy.
3. If the project is trusted, load its project policy.
4. Validate both documents and compose an effective policy.
5. Resolve relative filesystem paths against `ctx.cwd` and canonicalize security-sensitive paths.
6. Check platform support and required Sandbox Runtime dependencies.
7. Initialize `SandboxManager` with the effective policy and violation monitoring enabled.
8. Record the runtime generation and mark the session ready.
9. Set a visible `Sandlot` status in modes that support UI status.

Pi awaits asynchronous `session_start` handlers, so no model tool should execute before initialization completes. Tool implementations must nevertheless check runtime readiness themselves.

### 6.3 Session shutdown

On `session_shutdown`, Sandlot must:

1. Mark the runtime unavailable immediately.
2. Abort all active sandboxed invocations.
3. Wait for child process trees to exit or forcibly terminate them.
4. Perform per-command Sandbox Runtime cleanup where required.
5. Call `SandboxManager.reset()`.
6. Clear UI status and in-memory session state.

This lifecycle applies to quit, reload, new session, resume, and fork flows.

### 6.4 Reload and replacement safety

Each initialized runtime must have a generation identifier. Tool calls capture the active generation and reject results from a stale generation after session replacement or reload. Code running after a Pi reload must not reuse old extension or runtime state.

## 7. Tool routing

### 7.1 General rules

Each overridden tool must:

- Resolve paths relative to the current `ctx.cwd`, not a factory-time working directory.
- Require an initialized runtime.
- Pass a unique invocation ID to Sandbox Runtime. Pi's tool-call ID should be used when available.
- Honor the supplied `AbortSignal`.
- Preserve Pi's expected result and `details` shapes.
- Preserve Pi's output limits and truncation behavior.
- Throw on execution errors so Pi marks the result as an error.
- Never fall back to Pi's local implementation after a sandbox error.

Where possible, Sandlot should create tools using Pi's `createReadTool`, `createWriteTool`, `createEditTool`, `createBashTool`, `createLsTool`, and `createFindTool` factories with custom operations. This retains Pi's schemas and renderers.

### 7.2 Bash

The `bash` override must:

1. Pass the raw command to Sandbox Runtime.
2. Spawn the descriptor returned by `wrapWithSandboxArgv()` using `shell: false` at the host boundary.
3. Set the requested working directory.
4. Stream both stdout and stderr through Pi's `onData` callback.
5. Preserve Pi's timeout and cancellation behavior.
6. Kill the complete process tree on cancellation or timeout.
7. Run Sandbox Runtime's per-command cleanup after completion.
8. Annotate or otherwise expose violations associated with the invocation.

The same operations backend must be returned from Pi's `user_bash` event for `!` and `!!` commands.

### 7.3 Read, write, and edit

File operations must execute through a small packaged helper launched inside Sandbox Runtime.

The helper should use Node built-ins for filesystem operations and communicate through structured stdin/stdout. File contents must not be interpolated into shell commands. Paths must be passed in a way that does not permit host-shell injection.

Required operations include:

- Read a file as bytes.
- Check readable or writable access.
- Detect supported image MIME types.
- Write UTF-8 content.
- Create directories recursively.

`edit` should use Pi's normal edit implementation with sandboxed read, access, and write operations. This retains exact replacement semantics, mutation queuing, diffs, patches, and rendering.

The packaged helper and the selected Node executable must be readable but not writable from inside the sandbox.

### 7.4 Directory listing

`ls` should use sandboxed operations for:

- Existence checks.
- File/directory metadata.
- Directory entry listing.

Metadata sent over the helper protocol must be plain serialized data. Host code reconstructs only the minimal interface Pi expects, such as `isDirectory()`.

### 7.5 Find and grep

Search binaries and filesystem reads must run inside the sandbox.

`find` may use Pi's custom glob operation if every existence check and search operation is delegated into Sandbox Runtime.

Pi's current `grep` operations interface customizes path checks and context reads but still launches `rg` on the host. Sandlot must therefore override its execution path rather than relying only on that interface. Its output and details should remain compatible with Pi's built-in grep renderer, including:

- Relative file paths.
- Match limits.
- Context lines.
- Long-line truncation.
- Byte truncation.
- `.gitignore` behavior.

The same rule applies to any search implementation: the search process itself must be sandboxed, not merely its follow-up file reads.

## 8. Tool ownership and custom tools

Pi permits extensions to override built-in tools. A later-loaded extension could otherwise replace a Sandlot-protected tool with an unsandboxed implementation.

At session start, Sandlot should inspect the effective tool registry and verify ownership of every protected tool. A `tool_call` handler should fail closed when:

- A protected tool is no longer owned by Sandlot.
- A custom tool has not been explicitly trusted.
- Sandlot is not initialized or is shutting down.

The default custom-tool policy should be `deny`. User configuration may list trusted custom tool names. Trusting a custom tool means accepting that its implementation may access the host directly.

Commands and initialization code from installed extensions remain outside this guard and are part of the trusted extension boundary.

## 9. Configuration

### 9.1 Locations

Suggested configuration locations are:

```text
~/.pi/agent/sandlot.json   # trusted user policy
<project>/.pi/sandlot.json # optional project restrictions
```

The implementation should use Pi's configuration directory helpers rather than hardcoding `.pi` where applicable.

Project configuration must only be read when `ctx.isProjectTrusted()` is true.

### 9.2 Policy hierarchy

The user policy is the permission ceiling. A project policy may only tighten it.

Policy composition rules should include:

- `network.allowedDomains`: project entries must be semantically covered by the user allowlist. The effective list is the project list when supplied, otherwise the user list.
- `network.deniedDomains`: union user and project entries.
- `filesystem.allowWrite`: project paths must be contained within user-allowed paths. The effective list is the project list when supplied, otherwise the user list.
- `filesystem.denyWrite`: union user and project entries.
- `filesystem.denyRead`: union user and project entries.
- `filesystem.allowRead`: project exceptions must be a subset of user exceptions.
- Unix socket permissions: project configuration may remove permissions but not add them.
- Trusted custom tools: project configuration may remove trusted tools but not add them.
- Weaker isolation settings and Apple Events: only user configuration may enable them. Project configuration may disable them.

Invalid widening attempts must reject the project policy and leave Sandlot fail-closed. They must not be silently ignored.

### 9.3 Validation

Configuration must be validated before calling `SandboxManager.initialize()`. Unknown or misspelled security-sensitive keys should be rejected rather than stripped.

The extension should build strict schemas around Sandbox Runtime's exported schemas and include Sandlot-specific settings such as:

- `enabled`
- trusted custom tools
- child environment passthrough
- project policy behavior
- diagnostic options

Explicitly requested but unreadable or invalid configuration must be a hard error.

### 9.4 Recommended defaults

The default policy should prioritize security:

- Network allowlist is empty.
- `network.strictAllowlist` is true.
- Writes are limited to the current workspace, Sandlot's private per-session temporary directory, and Sandbox Runtime's required temporary paths. The private directory is an internal operational grant, not a policy write root.
- Reads of common credential locations are denied, including SSH, cloud, package-manager, Git credential, and Pi authentication/session files.
- Writes to project-local Pi configuration and extension locations are denied.
- Writes to `.env` files and common credential files are denied.
- Sandbox Runtime's mandatory deny paths remain enabled.
- Unix sockets are denied.
- Local port binding is denied.
- Apple Events are denied.
- Weaker isolation modes are disabled.
- Unknown custom tools are denied.

Because Sandbox Runtime's general read policy is deny-then-allow rather than deny-by-default, Sandlot must explicitly protect sensitive locations.

Users who need package registries, Git hosting, or other network services must add them to the trusted user policy. A project may then select a subset of those domains.

## 10. Environment and credentials

Sandboxed commands must not inherit Pi's complete host environment.

Sandlot should construct a safe child environment containing only necessary operational values, for example:

- `PATH`
- locale variables
- terminal-related variables where needed
- safe temporary-directory variables
- Pi's per-command session metadata when appropriate

Provider API keys and arbitrary host secrets must not be passed through by default.

The isolated wrapper always retains fixed, host-independent operational values for `PATH`, `LANG`, and `LC_ALL`. Before Sandbox Runtime initialization, trusted host code creates the current-UID-owned root, UID, and session components of `/tmp/sandlot/<uid>/session-<unpredictable>/` with exact mode `0700`, rejects symlinks, wrong ownership, non-directories, unsafe permissions, and identity changes, and sets `TMPDIR`, `TMP`, and `TEMP` to that same session path. Exact `0700` is required only at those three protected hierarchy components; current-UID descendant directories may have routine application modes, while recursive cleanup must verify no-follow directory type, current ownership, and stable identity before traversing each one. It grants write access only to that session directory as an internal operational Sandbox Runtime grant; it never grants `/tmp`, `/private/tmp`, a host Darwin temporary directory, or the whole `/tmp/sandlot` tree. The boundary owns an opening generation before asynchronous allocation or transport startup, rejects parallel opens, and makes reset cancel and consume any opening attempt before reset may return. Reset, initialization failure, poisoned-runtime handling, and normal shutdown may clean up only after every runner-owned protected execution and its supervised descendants have positively settled, the independent Sandbox Runtime service transport has positively terminated, and the recorded identities still match. Concurrent reset and poison handling must keep each detached transport in one owned shutdown record; service termination confirmation is monotonic and tied to a successful close of that record's generation, never inferred from transport absence in another caller. Service transport close does not by itself prove that separately spawned runner commands have exited. An indeterminate abort or descendant-supervision result retains cleanup authority and poisons the runtime. Creation rollback and later cleanup failures must surface both relevant errors, retain exact cleanup authority for retry, and never delete a replacement path. Environment deny or credential policy cannot replace these fixed temporary values with host values.

Advanced users may configure:

- Explicit safe environment passthrough.
- Explicit denied variables.
- Sandbox Runtime credential masking and host-scoped injection.

Credential masking should require TLS termination unless the user explicitly chooses Sandbox Runtime's less-safe plaintext behavior. Credential injection destinations must remain within the network allowlist.

Reset and shutdown clear the service's JavaScript references to credential sources. V8 does not guarantee physical zeroization of prior heap storage, so the design must describe this as reference clearing, not byte-level zeroization.

Pi's own model-provider requests run on the host and therefore do not require provider credentials inside the sandbox.

## 11. Network behavior

All sandboxed network access is deny-by-default and mediated by Sandbox Runtime's proxy infrastructure.

Sandlot should initialize violation monitoring and use a unique `commandId` for each invocation. Network or filesystem denials should be made visible in the associated tool result as concise `Blocked by Sandlot:` notices, while avoiding duplicate or stale violations. The one exact benign macOS `sysctl-read kern.iossupportversion` probe is suppressed; near matches and all other operation/target pairs remain visible, including unfamiliar Runtime operation names through a safe generic notice. `/sandlot` classifies and deduplicates the complete bounded store before retaining its ten newest material entries.

Allowing a broad domain such as `github.com` still permits possible exfiltration to resources on that domain. Documentation must explain that domain allowlisting limits destinations but does not necessarily limit accounts, repositories, URL paths, or request bodies. Sandbox Runtime TLS termination and request filtering may be supported later for users needing finer controls.

## 12. Failure behavior

Sandlot must fail closed in all of the following cases:

- Unsupported platform.
- Missing platform dependencies.
- Invalid configuration.
- Project policy attempts to widen permissions.
- Sandbox Runtime initialization failure.
- Sandboxed helper startup failure.
- Tool ownership collision.
- Runtime shutdown or replacement in progress.
- Unknown custom tool without explicit trust.

Failure should:

1. Block the operation.
2. Return an actionable error to the model or user.
3. Set an error status in UI-capable modes.
4. Never invoke the equivalent host operation.

An explicit user-level disable option may be provided, but it must be conspicuous and must not be controllable from project configuration.

## 13. User experience

Recommended UI and commands:

- Footer status: `🔒 Sandlot` with a compact summary.
- Error status when initialization failed.
- `/sandlot`: show platform, readiness, effective policy summary, dependency warnings, and recent violations.
- `/sandlot-reload`: safely run Pi's reload lifecycle after configuration changes.
- Optional diagnostics command that verifies representative allowed and denied operations.

All UI calls must be guarded appropriately for TUI, RPC, JSON, and print modes. Security must not depend on a confirmation dialog being available.

## 14. Platform requirements

Sandlot's first release supports macOS only. Linux/Bubblewrap support is deferred and unverified for this release. Windows is unsupported and out of scope for v1.

### macOS

- Sandbox Runtime uses `sandbox-exec`/Seatbelt.
- `ripgrep` is required by Sandbox Runtime.
- Apple Events must remain disabled by default because enabling them permits launching unsandboxed applications.
- Sandlot's immutable package-owned `mktemp` PATH shim is both protected from writes and explicitly trusted-readable, so it remains executable from denied package locations. It rewrites normal implicit shell forms, including empty `-t ''` and `--tmpdir=`, to products below the exact session `TMPDIR`. Absolute `/usr/bin/mktemp` and applications deliberately using `_CS_DARWIN_USER_TEMP_DIR` remain upstream limitations and do not justify granting the host Darwin temporary directory.

### Linux (deferred)

Linux/Bubblewrap is not a supported or release-verified boundary in the first release. Future support is expected to require Bubblewrap, `socat`, `ripgrep`, user-namespace/AppArmor configuration where applicable, rejected or clearly warned unsupported filesystem globs, and an explicit user-level opt-in for weaker nested-sandbox mode. Sandbox Runtime's mandatory nested-path scan behavior and general Linux lexical-alias collapse remain deferred upstream/runtime limitations.

## 15. Testing strategy

Development should follow test-driven development for security-critical behavior: write a failing test, implement the minimal behavior, and then refactor while keeping the suite green.

### 15.1 Unit tests

Unit tests should cover:

- Strict configuration validation.
- User/project policy composition.
- Domain subset and wildcard rules.
- Path containment and canonicalization.
- Dangerous-option inheritance.
- Environment sanitization.
- Runtime state transitions and generations.
- Tool ownership decisions.
- Command argument and helper protocol encoding.

### 15.2 Tool contract tests

Each overridden tool should be tested against Pi's expected behavior and result shape:

- Read text and images.
- Read offset and limit behavior.
- Write and recursive directory creation.
- Single and multiple edit replacements.
- Parallel mutation safety.
- Directory listing.
- Find glob and limit behavior.
- Grep regex, literal, case-insensitive, context, and limit behavior.
- Bash streaming, truncation, exit codes, timeout, and cancellation.

### 15.3 Security integration tests

For the first release, macOS Seatbelt integration tests must prove that:

- Workspace reads and writes succeed.
- Reads of protected credentials fail.
- Writes outside the workspace fail.
- Writes to `.pi`, Git hooks/config, and protected files fail.
- Disallowed network destinations fail.
- Explicitly allowed network destinations succeed.
- Secret host environment variables are absent or masked.
- Child processes inherit the same sandbox restrictions.
- Cancellation terminates descendants.
- Initialization failure blocks every protected tool.
- No protected tool uses a local fallback.
- Unknown and replaced tools are blocked.
- Violations are attributed to the relevant invocation.

### 15.4 Lifecycle tests

Tests should cover startup, reload, new session, resume, fork, and shutdown. Every replacement must reset the old runtime and initialize a fresh policy without leaking proxies or child processes.

### 15.5 Package smoke tests

Test installation and loading through the same mechanisms users will use:

- Local package path.
- Git package installation.
- Interactive or RPC startup.
- Print/JSON startup without UI.

## 16. Implementation sequence

1. Create package metadata, TypeScript configuration, and test harness.
2. Implement strict configuration schemas and policy composition using tests first.
3. Implement the fail-closed runtime state machine and Pi session lifecycle.
4. Implement a macOS sandboxed process runner with cancellation and violation attribution; defer Linux release support until its dedicated verification work is complete.
5. Override `bash` and intercept user bash commands.
6. Implement sandboxed file helper operations and override `read`, `write`, and `edit`.
7. Override `ls`, `find`, and `grep`, ensuring search binaries run inside the sandbox.
8. Add tool ownership and custom-tool guards.
9. Add status, diagnostics, commands, and documentation.
10. Run the macOS Seatbelt release gate and package smoke tests before the first release; add the Linux matrix only with verified Linux support.

Each step should finish with passing unit and integration tests before the next tool surface is added.

## 17. Acceptance criteria

Sandlot is ready for its first release when:

- Installing the package causes every new Pi session to initialize Sandlot automatically.
- All seven built-in coding tools and user bash commands are demonstrably sandboxed.
- Initialization or execution errors never result in unsandboxed fallback.
- The default policy blocks external writes, common secret reads, secret environment leakage, and network access.
- Project configuration cannot widen the trusted user policy.
- Unknown custom tools are blocked unless explicitly trusted.
- Session replacement and shutdown leave no child processes or proxy resources behind.
- macOS Seatbelt security integration tests pass. Linux/Bubblewrap release verification remains deferred.
- The README clearly documents the threat model, configuration, prerequisites, and limitations.

## 18. Future work

Possible later additions include:

- A separately installed `sandlot-pi` launcher that runs the entire Pi process inside Sandbox Runtime.
- A persistent sandbox worker if performance data justifies it.
- Interactive, temporary network permission prompts.
- TLS-terminated request-level network policies.
- Rich violation rendering and audit logs.
- Policy presets for common ecosystems.
- Stronger credential-masking recipes.

A whole-process launcher must remain separate from the extension architecture. It would need explicit access to provider endpoints, credentials, Pi configuration, package directories, and session storage, and should have a distinct threat model and policy.
